# Data model and contracts

SQLite canonical entities:
- resources(id UUID PK, type, display_name, description, icon, default_action, created_utc, updated_utc)
- resource_targets(id UUID PK, resource_id FK, kind, canonical_uri/path, device_selector, priority, arguments_json, working_directory, active)
- profiles(id UUID PK, name, theme_id, settings_json, created_utc, updated_utc)
- profile_resources(profile_id FK, resource_id FK, group_id, favorite, sort_position, overrides_json)
- groups(id UUID PK, profile_id FK, parent_id, name, ordering)
- tags(id UUID PK, name), resource_tags(resource_id, tag_id)
- layouts(id UUID PK, profile_id, surface, layout_json, version)
- dock_items(profile_id, resource_id, position, settings_json)
- launch_events(id UUID PK, request_id UNIQUE, resource_id FK, target_id, profile_id, device_id, source, launched_at_utc, status, error_code, duration_ms)
- metadata_cache(resource_id, target_id, inspected_utc, file_size_bytes, created_utc, modified_utc, availability, provenance, error_code)
- device_mappings(id, device_id, source_prefix, target_prefix, approved)
- schema_migrations(version PK, checksum, applied_utc)

All timestamps UTC in storage, localized for display. One request ID leads to one persistent launch event, with updates to that event if lifecycle has multiple outcomes. Missing resource/target is still a failed launch attempt if valid resource ID supplied.

Resource IDs never derive from paths, file size or name. A resource can belong to many profiles, multiple targets and groups; no per-profile re-creation required. Cascades and deletion/retention are explicit. Launch statistics must not overstate Windows Shell handoff as document load success.

Manual .swprofile export contains manifest with schemaVersion, application identity, exportedAt, selected profile and resources/layout/pins, optionally history (default OFF) and icon assets. Credentials/tokens excluded. Use contracts/*.schema.json and fixtures/ for detailed validation. Do not silently import executable actions or external connector secrets. 

Workspace action sequences (SW-014) are profile-scoped named records with 1–20 ordered steps. Each step stores a stable ID and references an existing resource in that profile plus an optional active target owned by the same resource. No command text, executable path, arbitrary arguments, conditions, or scripts are stored. Runs are explicitly requested by the user, use the standard validated launcher once per step, persist normal launch events, and stop after the first failed Shell handoff. A unique run request ID stores progress/results so retries return the prior result without launching again. Imported sequence definitions remain inert until a user explicitly runs them.

Usage history (SW-015) is profile-local. `usage_settings` controls recording, retention (30/90/365 days or indefinite), and excluded resource IDs. `launch_request_guard` is an independent replay ledger containing only request/resource/target/profile IDs, source, UTC time, outcome, error code, duration, and a hashed intent; it has no path, arguments, or free-form message and survives analytics retention/purge. `launch_events` contains only events the user has chosen to retain. Stop-recording suppresses new event rows without clearing existing rows; explicit purge and retention remove event rows while retaining replay guards. Terminal sequence run records are compacted when history is disabled, purged, or expired; in-progress sequence snapshots remain only for crash-safe resume.

Resource relationships (SW-016) are profile-local undirected edges between two distinct resources already assigned to that profile. Each edge has a stable UUID and a short user label; reversed endpoint pairs are duplicates. They are descriptive links only and never execute an action. Workspace snapshots are named checkpoints of dashboard and dock layouts plus the resource IDs present at capture time. Restoring updates layouts for resources that still belong to the profile, reports missing references, and does not delete resources, memberships, or cards. Snapshots are local profile data and do not launch resources.

SW-017 duplicates a resource only within a profile where the source is already assigned; it creates new resource/target UUIDs and never copies or launches files. Relocation previews map a user-entered source path prefix to a destination prefix for selected profile resources (or all matching profile resources), limited to file/folder targets. The preview includes the exact old/new target URIs and a token bound to the change set. Commit re-evaluates current state and applies only if the preview still matches, transactionally. This updates launcher references; it does not move, copy, scan, or delete filesystem contents.

SW-018 is an explicit, read-only discovery and import flow. The user selects a Start Menu folder, a directory to scan, or a supported bookmark file. Scans are bounded (maximum depth 4, 1,000 entries, 4 MiB per bookmark document), use a capability-opened root and no-follow child/file opens, reject observed symlinks/reparse points, and return inert candidate DTOs with source/provenance labels. The selected root is initially opened from its validated ambient path, and Windows `.lnk` metadata is read through `IPersistFile::Load` by path; a hostile same-user process may race those two operations by replacing the selected root or shortcut. This importer is user-initiated discovery, not an isolation boundary. Supported directory candidates are folders, regular files and `.url` internet shortcut files with `https` targets; Windows `.lnk` targets are metadata only and are never resolved or invoked. Bookmark import accepts Netscape-format HTML links whose target scheme is `https`. Scripts, executables' command arguments, embedded HTML/script actions and other URL schemes are never imported. Scanning never occurs implicitly or over whole drives/network shares.

The UI previews each candidate, exact target, provenance, and profile-duplicate match before explicit commit. The user can deselect any row and choose `skip existing` or `create another resource`; matching is by normalized candidate target within the destination profile and does not merge metadata. Commit revalidates profile membership and candidate bounds and inserts selected resources/targets/memberships in a single transaction; failure rolls back the entire batch. Commit re-scans and rejects changes to the source, candidate set, or profile duplicate matches since preview. No fixed time-to-live is imposed; the preview remains usable only while the rescanned state matches its token. No imported candidate is launched. Scanner limits and candidate targets are validated in Rust independently of UI filtering.

Usage queries and summaries share profile, inclusive UTC range, source, status, and resource filters. Pagination orders by UTC time then request ID for stable boundaries. CSV usage export includes request/resource IDs, UTC time, source, status, and duration only; it excludes paths, arguments, user-controlled resource names, and free-form failure text. Launch history represents requests recorded by this application on this device, not files opened in other applications.

Dashboard widgets (SW-019) are stored with the profile's dashboard layout and therefore travel with workspace snapshots and manual profile archives. A layout may contain up to 20 reusable templates and 50 positioned instances; Dock layouts contain neither. The initial built-in kinds are resource shortcuts (1–12 same-profile resource IDs), recent launches (limit 1–20), launch summary (7-day, 30-day or all recorded history), and related resources (same-profile anchor ID and limit 1–12). Widget IDs are UUIDs and instances reference a template in the same layout. Older layouts with no widget fields deserialize as empty; imported references are remapped through the same resource map as archive resource IDs. These are inert, app-rendered data views and cannot contain scripts or arbitrary content.

SW-020 device path mappings are installation-local preferences keyed by a random UUID stored with the per-user OS app-local settings outside any portable bundle; neither hostname nor hardware identifiers are collected. A user can rename the local device label. Copying a portable bundle/database to another computer therefore creates a fresh local identity, and mappings keyed to the old UUID remain inert there. Each approved rule translates one absolute file/folder target path prefix to another on this installation only. Supported paths are absolute Windows drive-letter or UNC paths; `file:` URIs, extended-length paths and device namespaces are rejected. Canonical resource targets and profile archives are unchanged; device identity and mappings are omitted from profile export. On another installation imported resources retain their original paths until the user previews and approves local mappings there. Mapping previews list every affected resource/target and exact resulting path, and commits are rejected if the current target set or mapping state differs from the preview. Rules are bounded to 100 per installation and 5,000 affected targets per preview. Prefixes match only at path-component boundaries; Windows comparison is case-insensitive. When rules overlap, the longest matching source prefix wins, then stable mapping UUID order. Only active file/folder targets are eligible; URLs, apps, shortcuts, arguments and working directories are not rewritten. Mapping rules never scan, copy, move, create, or launch files. Resolved local paths are used only for explicit launch handoff and continue to report the canonical target identity in history.
