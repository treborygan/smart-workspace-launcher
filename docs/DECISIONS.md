## SW-017 interpretation — duplicate and relocation assistant

The roadmap says “duplicate/missing relocation” but does not define whether relocation physically moves user files. To keep the assistant local, reversible and bounded, duplication creates a new profile resource and new target UUIDs while leaving filesystem contents untouched. Relocation is an explicit preview-and-confirm mapping of stored file/folder target path prefixes; it never copies/moves/deletes files or scans directories. Commit is bound to the exact preview and revalidates source URIs/ownership transactionally. Non-file/folder targets are excluded.

## SW-020 interpretation — per-device paths and portable migration

Device path mappings are local launch-resolution preferences. Each installation receives a random UUID stored with per-user OS app-local settings outside any portable bundle; users can set a friendly label, but the app does not collect hostnames or hardware identity. Copying a portable bundle/database to another computer therefore creates a fresh local identity and old device-keyed rules stay inert. A mapping is created through an exact preview and explicit commit, applies only to file/folder canonical path prefixes at launch time, and never rewrites stored resource data. Supported paths are absolute Windows drive-letter or UNC paths; file URIs, extended-length paths and device namespaces are rejected. Path components must match at boundaries. Windows comparison is case-insensitive; overlapping rules use longest-prefix then stable UUID order. A preview is invalidated by any change in the mapping list or affected target set; commit is transactional. Rules do not change arguments or working directories and do not inspect, copy, move, create, or launch filesystem objects. Mapping/device preferences are excluded from profile archives: portable profile import retains source paths and requires the destination installation to configure and approve its own mappings.

## SW-021 interpretation — permissioned extension registry and SDK boundary

The SW-021 registry stores validated extension manifests, modules and a user's explicit capability grants. Extensions default to disabled; requested and granted capabilities are separate sets, grants must be a subset of requested capabilities, and unknown capabilities or fields are rejected. Manifest IDs are lowercase reverse-DNS labels (maximum 255 ASCII characters); name is 1–80 characters and description 1–240, both trimmed and nonblank; semantic version is a bounded three-number `MAJOR.MINOR.PATCH`, SDK version must be `1.0.0`, and at most two unique capabilities may be requested. The manifest is limited to 4 KiB when serialized.

An extension package is an explicitly selected `.swext` ZIP containing exactly `manifest.json` and `module.wasm`, with no directory entries, duplicate names, symlink entries, additional files, traversal paths or scripts. Compressed package size is at most 2.1 MiB; manifest is at most 4 KiB and Wasm module at most 2 MiB. Preview validates both entries and hashes their content without executing the module; it returns a random opaque in-memory token bound to the exact package path and digest. Tokens expire after five minutes, are single use, at most 32 are retained, and app restart invalidates them. Install atomically consumes a matching token, rereads the package and commits only if its digest still matches. ZIP decompression and Wasm validation happen before acquiring the app-wide database mutex; only the final registry transaction holds it. An installed extension ID cannot be replaced in place; removal is required and deletes its grants. The module is executed only by an explicit user action while the registry entry is enabled. The wasmi interpreter receives modules whose import section is empty: function, table, memory and global imports are rejected. Structural parsing/validation is capped at 512 types and functions, 64 parameters and 64 results per function type, 256 globals, 1,024 locals per function and 16,384 total locals, 100,000 operators, 64 data segments, 64 element segments, 16 standard sections, and 8 custom sections with 64 KiB combined payload; defined tables are rejected; compilation is deferred until a Run action and occurs once per run. Runtime is bounded to one memory with a two-page (128 KiB) limit, 1,000,000 fuel, recursion depth 128, value stack 64 KiB, 64 KiB input and 64 KiB output. The required ABI exports `memory`, `alloc(i32)->i32`, and `handle(i32,i32)->i64`; the returned i64 packs output pointer in its high 32 bits and output length in its low 32 bits. Every pointer and length is checked before host memory access. Modules with a Wasm start section are rejected before instantiation, so no start code runs. Run snapshots the module, grants and input under the database mutex, executes and parses output without it, then reacquires the mutex only to verify current profile membership for returned resource IDs.

Capabilities are read-only data supplied in the invocation JSON; there are no host calls. `resource_metadata.read` grants up to 200 active-profile resource summaries (UUID, display name, type, category, tags and favorite state), never targets, paths, URLs, arguments or file contents. Summaries are ordered by resource UUID, and the backend appends them only while the full serialized invocation remains at most 64 KiB. The `truncated` flag is true when either the count or byte limit omits any resource. `workspace_summary.read` grants aggregate counts only. The input schema requires the data field for each granted capability and forbids it when the capability is absent; input contains SDK version and exact granted capability names. The module returns only bounded plain-text suggestions referencing resources in the selected profile (maximum 20 suggestions, each with up to 12 resource UUIDs); malformed JSON, unknown fields, controls, oversized output and out-of-profile IDs are rejected. Suggestions are displayed as data only, never execute or launch an action, and are not persisted as history. Extension state and outputs are not exported in profile archives. Removal deletes its module and grants. This boundary excludes all filesystem, process, network, clock, random, shell, launch and secret access.

## SW-018 interpretation — Start Menu, directory and bookmark import

Import is user-selected, read-only discovery followed by a preview and explicit transactional commit. It does not scan drives or network shares automatically and never launches a discovered item. A directory scan is bounded to depth 4 and 1,000 entries, uses a capability-opened root with no-follow child/file opens, rejects observed symlinks/reparse points, and discovers only folders, regular files, and `.url` shortcuts containing safe HTTPS targets. The selected root is initially opened from its validated ambient path, and Windows `.lnk` metadata is read with `IPersistFile::Load` by path, leaving a narrow same-user replacement race for those operations; this user-initiated scanner is not an isolation boundary. A Windows Start Menu folder uses the same bounded scanner; Shell Link metadata is never resolved or invoked. Bookmark import accepts Netscape-format HTML and HTTPS links only (4 MiB input maximum). Other protocols, scripts, command arguments and embedded actions are discarded.

Preview labels each row with source and provenance and marks same-target resources already in the destination profile. Users select rows and choose `skip existing` or `create another resource`; no implicit metadata merging occurs. Commit receives the source descriptor, selection keys, and preview digest; it repeats the bounded scan and rejects stale/mutated source, candidate, or duplicate-match state before a single SQLite transaction creates selected resources, targets, and profile memberships. A batch failure rolls back completely. No fixed preview TTL is imposed; a preview remains valid only while the recomputed state matches. This scan is not an ongoing watcher or a complete index of the device.

## SW-019 interpretation — reusable dashboard widget templates

Widgets are profile-local data views rendered only by the application. The first built-in kinds are `resource_shortcuts`, `recent_launches`, `launch_summary`, and `related_resources`; template configuration contains only bounded UUID references and display limits/periods. A profile may store up to 20 templates and 50 positioned dashboard instances. Template names are 1–60 characters; resource lists contain 1–12 unique same-profile resource UUIDs; related-resource anchors must belong to the profile. Instances are bounded to the existing 12-column/9999-row dashboard geometry. Widgets are not supported on the Dock. Old layouts without widget fields remain valid; import/export and workspace snapshots preserve widget data. Templates and instances contain no script, HTML, URL, executable, query language, callback, or arbitrary extension payload. Resource launch buttons still use the ordinary validated launch command; history widgets only report this application's recorded events and respect profile history settings. Unknown kinds/config fields are rejected.
